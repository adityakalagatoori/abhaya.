ONE-LINE PRODUCT DEFINITION
ABHAYA is a dynamic safety-aware navigation system that evaluates the safety of a journey using time, infrastructure, activity, reports and location context, then continues that safety logic through ride-hailing pickup/drop-off, route-deviation monitoring and the user's final walk.
2. The Current ABHAYA Idea — Preserved, Not Replaced
The uploaded proposal identifies the central problem as the weakness of existing safety-navigation systems: they often depend on static crime/risk zones, have reporting gaps, and do not adequately account for how risk changes with time and local conditions. The proposal also identifies the lack of proactive intent/anomaly detection. These are the problems ABHAYA is designed around. fileciteturn2file0L1-L4

3. What Is Actually Unique About the Existing Idea?
The team should not claim that every individual component is globally unprecedented. Computer vision, risk-aware routing, anomaly detection and LLM-based explanations each exist as technologies. The stronger and more defensible innovation claim is the way the team's existing components are combined into one continuous safety journey.
THE UNIQUE PRODUCT STORY
ABHAYA does not stop at choosing a route. It carries the same safety decision from the route → to the ride pickup/drop point → through the live ride → and into the final walk.
This is a refinement of the current idea, not a new feature.

SafeDrop is the clearest concrete demonstration of ABHAYA's philosophy. The destination pin can be technically correct but physically unsafe. 6. Detailed Product Specification
6.1 Dynamic Risk-Aware Navigation
This remains the main product. The system should not treat safety as a fixed red/green map overlay. It combines the factors already specified in the proposal: crime history, infrastructure condition, crowd/activity levels, reports, nearby safety points and time of travel. The uploaded proposal specifically identifies static spatiotemporal blindness as a gap in existing platforms. fileciteturn2file0L1-L4
Implementation:
Represent the road network as a graph.
Attach the existing safety factors to road segments.
Normalize the factors to comparable ranges.
Apply time-of-travel context so the risk estimate can change with the expected travel time.
Generate multiple candidate paths using standard graph routing.
Evaluate each candidate using safety and travel-time trade-offs.
Return a route that balances safety and practical travel time rather than an absurdly long detour.
A practical prototype objective can use the proposal's multi-objective form:
ROUTING OBJECTIVE
R = w1(Safety) - w2(Time Delay) - w3(Infrastructure Risk)
The weights should be configurable during testing. The prototype should demonstrate the trade-off clearly rather than claiming that one fixed weight is universally correct.

7.1 SafeDrop — Intelligent Drop-off Selector
Problem:
A driver may stop at the exact destination pin even if that location is a poorly lit alley, side gate or isolated road.
Existing solution:
When the user enters a destination, audit nearby possible drop points using the existing CV/infrastructure information.
Prefer a well-lit/open point that leaves only a short walk, when the data supports it.
Present the chosen point as the safer practical drop location.
Prototype:
Create 2–4 nearby simulated drop points around one destination.
Assign infrastructure evidence to each point.
Run the same existing CV/risk scoring logic.
Select the safer practical point.
Show the difference visually: exact destination vs recommended drop point.
Demonstrate that the safer point may be slightly farther but materially better supported by the available infrastructure evidence.
PRESENTATION LINE
ABHAYA does not only ask 'Where is the destination?' It asks 'Where should the passenger safely get out?'

8. Complete User Journey
This is the flow the PPT, UI and demo should all follow:
User enters destination.
ABHAYA evaluates available crime, infrastructure, activity, reports, safety-point and time context.
Dynamic Risk-Aware Navigation generates route options using the existing safety/time trade-off.
User sees the recommended route and concise reason.
If using ride-hailing, the system identifies a safer practical pickup/waiting point when available.
Near the destination, SafeDrop identifies the safer practical drop-off point.
During the ride, RouteGuard compares live vehicle movement with the expected route and risk context.
If meaningful deviation occurs, the existing discreet check-in / escalation flow is activated.
When the ride ends, WalkGuard continues for the defined five-minute final walking period.
Behavioral anomalies can activate the existing response flow.
The LLM/RAG layer can convert relevant underlying information into concise human-readable safety guidance.

11. Risk Scoring — Keep It Explainable

24.2 Dynamic Risk-Aware Navigation — Best Implementation
Existing feature: safety-aware routing using crime, infrastructure, crowd/activity, reports, nearby safety points and time of travel.
Do not implement it as...
Implement it as...
Why this is more distinctive
A static red/green heatmap.
A road-segment graph whose risk is recalculated for the expected time the user reaches each segment.
The route is evaluated against journey timing, not just current map colour.
One black-box “safety score”.
Factor-level evidence: lighting, reports, crime/history, activity and nearby safety context.
Every route decision can be explained.
A route that simply avoids all risk.
A safety/time trade-off with a configurable practical detour.
Prevents unrealistic 'safest = 45 minutes longer' results.
Recommended implementation:
Divide the road network into graph edges.
For each edge, store the existing risk factors separately.
When a journey starts, calculate the expected arrival time for every candidate edge.
Evaluate the edge using the conditions relevant to that expected time.
Attach the evidence IDs that caused the score.
Generate candidate routes.
Compare total travel time and total risk exposure.
Return the route with the best practical trade-off.
UNIQUE IMPLEMENTATION LINE FOR PPT
ABHAYA does not assign one permanent safety label to a road. It evaluates the road in the context of when the user is actually expected to traverse it.

29. Questions Judges May Ask — Implementation Answers
Question
Answer the team should give
What is actually novel here?
The existing features are connected through a common risk/evidence/journey representation, so route selection, SafeDrop, RouteGuard and WalkGuard operate on the same safety context.
Why not just use Google Maps?
The proposal is not replacing normal navigation; it adds the existing safety-specific context and ride-hailing safety continuity.
How do you know a road is unsafe?
We do not claim certainty. We combine available evidence such as infrastructure, historical reports, activity and time context and expose the basis of the decision.
Why use computer vision?
To generate infrastructure evidence such as lighting/visibility/open-establishment information instead of relying only on historical reports.
Why use DRL if A* works?
A* provides the feasible baseline; DRL is the advanced formulation for learning the same multi-criteria trade-off.
What if the user deviates intentionally?
Deviation alone is not treated as danger. The system evaluates whether the new route materially changes the risk context.
Why WalkGuard?
Because the current ride-hailing concept explicitly extends monitoring into the post-ride final walk.
Why SafeDrop?
The exact destination pin may not be the safest physical stopping point; nearby candidate points can be evaluated using the same existing risk intelligence.
Can this work without a live Uber API?
Yes for the prototype: use a simulated/recorded ride flow while preserving the same API boundary that a future integration would use.
